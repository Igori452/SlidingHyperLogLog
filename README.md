## О проекте

Проект реализует кастомную агрегатную функцию `sliding_count_distinct`, которая позволяет приближённо подсчитывать количество уникальных элементов (пользователей, IP-адресов, сессий) за заданный интервал времени без сортировки и без создания временных файлов на диске.

Основные возможности:
- Агрегатная функция `sliding_count_distinct(timestamp, value, interval, start_time)`.
- Оценка кардинальности по алгоритму HyperLogLog с линейной поправкой при малых значениях.
- Фиксированное потребление памяти (около 64 КБ на запрос).
- Отсутствие временных файлов на диске.
- Относительная ошибка около 1.6% при `m = 4096` регистров.



**`benches/`** — результаты экспериментов: три файла `research_100.txt`, `research_200.txt`, `research_500.txt` с логами запусков `EXPLAIN (ANALYZE, BUFFERS)` и реальным временем выполнения.

**`psql-extension/`** — обёртка для PostgreSQL: ядро алгоритма (`SlidingHyperLogLog-API/`), файл обёртки `pg_sliding_hll.cpp`, SQL-скрипт расширения и `Makefile` для сборки через PGXS.

**`tests/`** — тесты и генератор данных:
- `csv_generator/` — Python-скрипт для генерации синтетических датасетов;
- `sql/` — SQL-скрипты `big_data_*.sql`, `count_query_*.sql`, `HLL_query_*.sql`;
- `SlidingHyperLogLogTests.cpp` — тесты ядра на C++.

**`CMakeLists.txt`** — сборка изолированных тестов ядра (без PostgreSQL).

**`Makefile`** — автоматизация запуска Docker-контейнера, генерации данных и выполнения запросов.

## Требования

Для работы и экспериментов (через Docker) требуется:

**Для Ubuntu / Debian / WSL:**
```bash
sudo apt update
sudo apt install -y build-essential cmake g++ postgresql-server-dev-16 python3
```

*Полный список требований:*
- **C++20** (компилятор `g++` версии 10 или выше / `clang`).
- **CMake** (версия 3.16 или выше, для изолированных тестов ядра).
- **PostgreSQL 16** и заголовочные файлы разработчика (**PGXS** / `postgresql-server-dev-16`).
- **Python 3** (для работы скрипта генерации датасета).

## 1. Сборка и подключение расширения

### Сборка

```bash
cd psql-extension
make
```

`Makefile` использует PGXS — стандартный механизм сборки расширений PostgreSQL. Он компилирует обёртку `pg_sliding_hll.cpp` и ядро `SlidingHyperLogLog.cpp`, а затем компонует их в разделяемый модуль `sliding_hll.so`.

### Установка
```bash
sudo make install
```
Файлы расширения (`sliding_hll.so`, `sliding_hll--1.0.sql`, `sliding_hll.control`) копируются в системные каталоги PostgreSQL.

### Подключение
В `psql` или `.sql` файле:
```sql
CREATE EXTENSION sliding_hll;
```

## 2. Запуск тестов
Проект использует Docker для изоляции PostgreSQL и воспроизводимости экспериментов. Все команды выполняются через `Makefile` в корне проекта.

### Программное окружение Docker-контейнера

Для обеспечения 100% воспроизводимости результатов бенчмарков все тесты запускаются в изолированном Docker-контейнере.

Внутри контейнера развернуты и сконфигурированы следующие компоненты:

| Компонент / Пакет | Версия | Назначение в рамках исследования |
| :--- | :--- | :--- |
| **Базовый образ ОС** | Debian (Debian Bookworm-slim) | Стабильное системное окружение |
| **PostgreSQL** | `16` (Официальный дистрибутив) | Целевая реляционная СУБД для тестирования |
| **Citus Data `postgresql-hll`** | `master` (Последний коммит) | Встроенное расширение HyperLogLog от Citus Data |
| **SlidingHyperLogLog** | `1.0` (Текущая сборка) | Разрабатываемое расширение (копирует внутрь уже собранные файлы) |
| **Пакет `build-essential`** | `gcc` / `g++` 12+ (Этап сборки) | Компиляция исходного кода расширений из С-артефактов |
| **Пакет `postgresql-server-dev-16`** | `16` (Этап сборки) | Заголовочные файлы СУБД и макросы сборщика **PGXS** |


### Сборка образа
```bash
make build
```
Создаётся Docker-образ `pg-test` на основе PostgreSQL 16 с установленным расширением.

### Запуск контейнера
```bash
make run
```

Контейнер `pg-test-container` запускается на порту `5432` с параметрами:
- пользователь: `test_user`;
- пароль: `test_password`.


### Запуск тестов

После поднятия контейнера доступны три типа команд.

#### Наполнение данными (`sql-data-*`):
```bash
make sql-data-100   # создать таблицу и загрузить 100 млн записей
make sql-data-200   # 200 млн записей
make sql-data-500   # 500 млн записей
```
Каждая команда выполняет SQL-скрипт `tests/sql/big_data_*.sql`, который создаёт таблицу `user_logs`, загружает CSV через COPY и строит индекс по `viewed_at`.

**Важно:** выполнять стоит только одну из команд `sql-data-*`. Каждая команда начинается с `DROP TABLE`, поэтому последующая команда стирает данные от предыдущей. Если нужно переключиться на другой датасет — просто выполните соответствующую команду, она пересоздаст таблицу.

#### Точный запрос (`sql-count-*`):
```bash
make sql-count-100   # COUNT(DISTINCT) для data_100
make sql-count-200   # для data_200
make sql-count-500   # для data_500
```
Каждая команда выполняет SQL-скрипт `tests/sql/count_query_*.sql`. В выводе — план выполнения (EXPLAIN ANALYZE) и время.

#### HLL-запрос (`sql-hll-*`):
```bash
make sql-hll-100   # sliding_count_distinct на data_100
make sql-hll-200   # на data_200
make sql-hll-500   # на data_500
```
Каждая команда выполняет SQL-скрипт `tests/sql/HLL_query_*.sql`. В выводе — план выполнения и приближённое значение кардинальности.

#### Нагрузочное тестирование и исследование деградации производительности

В рамках научной работы реализована методология оценки деградации времени выполнения запросов при дефиците ресурсов. 

Тестирование разделено на два сценария: **точечные специализированные тесты** и **комплексные нагрузочные тесты**.

##### 1. Подготовка фоновой нагрузки (Занятие воркеров)
Перед выполнением любых нагрузочных тестов необходимо искусственно занять параллельные процессы СУБД. Для этого в отдельном терминале запустите команду:
```bash
# Занимает фоновые процессы. По умолчанию NUM_QUERIES=4, DURATION=120 секунд
make load-workers NUM_QUERIES=8 DURATION=300
```
Скрипт `fill_workers.sh` внутри контейнера утилизирует доступные пулы параллельных потоков СУБД, создавая условия для ресурсного голодания.

##### 2. Точечные тесты деградации (Специализированные SQL-скрипты)
Пока фоновые воркеры заняты (`make load-workers`), во втором терминале запускаются точечные скрипты для фиксации аномалий и деградации производительности:

* **Для стандартного (встроенного) алгоритма HLL:**
  ```bash
  make sql-load-hll-200
  make sql-load-hll-500
  ```
* **Для расширения `citusdata/postgresql-hll`:**
  ```bash
  make sql-load-extern-hll-200
  make sql-load-extern-hll-500
  ```

##### 3. Комплексные нагрузочные тесты (Стандартные SQL-скрипты под нагрузкой)
Для симуляции реальной многопоточной среды параллельно с запущенным `make load-workers` выполняются стандартные бенчмарки на разных объемах данных. Это позволяет измерить чистую разницу во времени отклика:
```bash
# Тестирование ядра (sliding) на 100, 200 и 500 млн записей
make sql-hll-100
make sql-hll-200
make sql-hll-500

# Тестирование встроенного HLL-расширения на тех же объемах
make sql-extern-hll-100
make sql-extern-hll-200
make sql-extern-hll-500
```

##### Важный параметр экспериментов: Изоляция последовательного выполнения
Чтобы исключить влияние оптимизатора параллельного сканирования PostgreSQL (Parallel Sequential Scan) и точечно измерить чистую производительность алгоритма в рамках **одного потока**, во всех вышеперечисленных SQL-скриптах зашит параметр параллелизма.

Для переключения между параллельным и строго последовательным режимами выполнения:
1. Откройте нужный SQL-скрипт в папке `tests/sql/` (например, `load_HLL_query.sql` или `HLL_query_100.sql`).
2. Найдите и **раскомментируйте** (или закомментируйте обратно) следующую строку в самом начале файла:
   ```sql
   SET max_parallel_workers_per_gather = 0;
   ```
   * При значении `0` планировщик принудительно отключает параллельный сбор данных, что позволяет зафиксировать чистую деградацию времени работы расширения без компенсации со стороны многопоточности СУБД.


### Изолированные тесты ядра (без PostgreSQL)

## 3. Генерация датасета

Так как готовые датасеты в совокупности весят около 20 ГБ, они не хранятся в репозитории. Для воспроизводимости экспериментов вы можете сгенерировать их локально.

### Быстрый запуск через Makefile
Команды автоматически генерируют стандартные датасеты исследования и сохраняют их под общим именем `data.csv` в директорию `tests/csv_generator/`:
```bash
make generate-100   # 100 млн строк, 100к уникальных, 1 год  (~2.5 ГБ)
make generate-200   # 200 млн строк, 60 млн уникальных, 3 года (~5.0 ГБ)
make generate-500   # 500 млн строк, 450 млн уникальных, 5 лет (~12.5 ГБ)
```

### Запуск с кастомными параметрами (напрямую через Python)
Вы можете гибко задать объем данных и имя файла, передав аргументы в скрипт в следующем порядке:
`python3 csv_generator.py [строк] [уникальных_id] [кол-во_дней] [путь_к_файлу]`

**Важно:** Файл **обязательно должен лежать в папке `tests/csv_generator/`**. Docker монтирует именно эту директорию на хосте в `/tmp` внутри контейнера. Соответственно, внутри контейнера ваш файл будет доступен по пути `/tmp/ваше_имя_файла.csv` (и этот же путь нужно будет указать в вашем SQL-скрипте для `COPY`).

Пример запуска из корня проекта:
```bash
python3 tests/csv_generator/csv_generator.py 5000000 50000 30 tests/csv_generator/my_custom_data.csv
```
